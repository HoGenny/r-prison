# Code Review Guide (팀 코드리뷰 규칙)

> 목표: **리뷰가 무섭지 않게**, 그리고 **서로 성장하는 리뷰** 만들기

---

## 1) 리뷰는 “검사”가 아니라 “품질 안전장치”

- 리뷰의 목적은 사람 평가가 아닙니다.
- **버그 예방 / 팀 이해도 공유 / 유지보수성 확보**가 목적입니다.

---

## 2) 리뷰 요청자가 지켜야 할 것

### ✅ PR을 작게 만들기
- PR이 너무 크면 리뷰가 불가능해집니다.
- 가능하면 기능 하나 단위로 쪼개세요.

### ✅ PR 설명을 “동료가 이해할 만큼” 적기
- 변경 이유(왜) + 영향 범위(무엇)를 중심으로 작성
- 테스트 방법 필수

### ✅ 리뷰어가 쉽게 볼 수 있게 하기
- UI 변경이면 스크린샷 첨부
- API 변경이면 요청/응답 예시 포함

---

## 3) 리뷰어가 지켜야 할 것

### ✅ “고치세요”보다 “이유 + 대안”
- ❌ “이거 별로인데요”
- ✅ “이 방식이면 나중에 유지보수가 어려워서, 함수로 분리하는 게 좋아요.”

### ✅ 초보자 팀 리뷰 우선순위
1. **앱이 깨지는가?** (크래시/에러)
2. **기능 요구사항을 만족하는가?**
3. **팀원이 이해 가능한 코드인가?**
4. **리팩토링/스타일은 마지막**

---

## 4) 리뷰 체크리스트 (가볍게 보기)

- [ ] 기능이 정상 동작하는가?
- [ ] 예외 처리(실패 케이스)가 최소 1개 이상 있는가?
- [ ] 변수/함수 이름이 의도를 설명하는가?
- [ ] 불필요한 코드/주석/로그가 없는가?
- [ ] 복잡한 로직에 한글 주석이 있는가?
- [ ] 테스트 방법이 PR에 적혀 있는가?

---

## 5) 리뷰 결과 처리 규칙

- **Approve**: 바로 Merge 가능
- **Request changes**: 수정 후 재요청
- **Comment**: 참고 의견 (필수 수정은 아님)

> 수정 요청을 받으면 “기분 상하는 것”이 아니라 “품질이 올라가는 것”으로 생각합니다.

---

## 6) 리뷰 시간이 오래 걸릴 때

- PR 올린 후 **24시간 내** 최소 코멘트 1개를 남깁니다.
- 코어타임에 PR 리뷰를 몰아서 처리하는 것도 좋습니다.
